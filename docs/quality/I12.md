## Evidence and changes

The unchanged packaged keyboard probe reproduced its previous exit 1. An independent minimal AppKit experiment also remained inactive after three seconds with both a nested run loop and asynchronous callbacks. A regular-policy variant reported that activation policy was accepted and launch was finished, but the console session reported **locked** and the window remained inactive/non-key/non-main. This establishes a current qualification limitation; it does not prove the cause of every earlier probe failure or establish product behavior on an unlocked session.

`KeyboardSmokeJourney` now requests activation, returns to AppKit's outer event loop and checks active/key/main readiness against a monotonic three-second deadline. The probe only creates its fixture editing controls after readiness. Timeout remains exit 1 and explicitly states that shortcuts were not exercised, including observed lock context. It never substitutes a skip or successful startup for a failed keyboard journey. The actual event-loop journey still uses the production settings window and menu with fixture text and a private clipboard responder. Native tests separately prove text Undo/Redo in a real settings field; those tests do not establish automatic active-app routing.

Apple documents that [activation can lag the request](https://developer.apple.com/documentation/appkit/nsapplication/activate(ignoringotherapps:)) and that [NSApplication distributes Window Server events](https://developer.apple.com/documentation/appkit/nsapplication). Returning to its event loop is appropriate; the locked-host experiment did not demonstrate that the former nested wait caused the failure.

The fullscreen fallback previously erased the distinction between a known desktop and unavailable detection. A native regression check demonstrated that Diagnostics had no fullscreen capability row or settings link: **one test, two assertion failures, zero unexpected failures** before the change. The new `Core/Displays/FullscreenSnapshot` records requested, covered and unavailable displays. The private SkyLight adapter remains runtime resolved; failed, negative and unknown Space types stay unavailable. `ScreenBarController` receives an injectable reader and uses its same result for bar visibility and instance diagnostics. Unknown displays keep their bars visible. Hiding-disabled active displays do not need a private query, and unchanged results do not repeatedly notify settings.

Diagnostics now shows waiting, disabled, available, partial and unavailable fullscreen states, includes the same entry in its report, and links to Layout. A changed display scope waits for a matching sample rather than retaining an unrelated capability claim. Refresh status explicitly retries visibility alongside provider/workspace health. Report assembly is separate from the clipboard action, permitting verification without changing the personal pasteboard. The section title is now “Integrations,” covering providers and display health. Two fresh fixtures show unavailable and recovered detection.

Ownership and backend-contributor entry points are documented in the [architecture guide](../ARCHITECTURE.md). These changes do not remove remaining shared feature state or create separately enforced package boundaries.

```sh
.build/ConstellationBar.app/Contents/MacOS/ConstellationBar --startup-smoke-test --keyboard-smoke-test
```

```text
KEYBOARD_UI_FAILED: Keyboard journey: Activation timed out (active=false, key=false, main=false, canKey=true, screenLocked=true). An unlocked interactive session is required; shortcuts were not exercised.
```

Active-app responder-chain shortcuts and text Undo/Redo remain unqualified. The current lock context is evidence about this session, not successful keyboard evidence or a retroactive diagnosis of earlier checkpoints. No screen unlock or security-setting change was attempted.

No installed app, personal configuration, permissions, login registration, Calendar/Reminder records or personal clipboard were changed.
